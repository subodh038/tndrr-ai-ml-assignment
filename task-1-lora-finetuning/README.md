# Task 1: LoRA Fine-Tuning on Qwen2.5-0.5B-Instruct

Fine-tune a small language model to convert natural-language calendar requests
into structured JSON using **LoRA (Low-Rank Adaptation)** via PEFT + TRL.

---

| Item | Detail |
|---|---|

| Fine-tuning method | LoRA (rank=16) |
| Dataset | 720 NL→JSON examples (6 action types) |
| Training environment | Google Colab (GPU required) |
| Local environment | Python 3.12, CPU-only PyTorch |

## LoRA Hyperparameter Justification

| Parameter | Value | Reason |
|---|---|---|
| `r` (rank) | **16** | Enough expressive power for slot-filling; rank-16 adds ~1-2% extra parameters. Too low (r=4) under-fits; too high (r=64) wastes memory. |
| `lora_alpha` | **32** | Effective scale = α/r = 2.0. Standard default; keeps adapter updates at a sensible magnitude without tuning the base LR. |
| `lora_dropout` | **0.1** | Light regularisation on the low-rank paths; reduces overfitting on a 700-example dataset. |
| `target_modules` | **q, k, v, o projections** | Attention projections carry task-specific sequence transformation. Including all four (not just q+v) gives better coverage. |
| `bias` | **none** | No bias terms trained; reduces extra parameters and is standard for causal-LM LoRA. |
| `learning_rate` | **2e-4** | 10× higher than typical full fine-tuning (2e-5). Only adapters are trained, so a higher LR is safe and faster. |
| `warmup_ratio` | **0.05** | 5% warmup steps prevent early gradient spikes when starting from random LoRA A/B init. |
| `lr_scheduler_type` | **cosine** | Smooth decay; avoids hard LR drops that can cause loss spikes near end of training. |
| `per_device_train_batch_size` | **4** | Fits in T4 16 GB VRAM with fp16 and seq_len=512. |
| `gradient_accumulation_steps` | **4** | Effective batch size = 4×4 = 16; improves gradient stability. |
| `num_train_epochs` | **3** | Small dataset (503 train examples) → risk of overfitting beyond 3 epochs. |

## 7B Model GPU Memory Summary

Theoretical calculations (see Cell 14 in the notebook):

| Strategy | Approx. VRAM | Trainable Params | Fits On |
|---|---|---|---|
| Full fine-tuning (FP32) | ~112 GB | 7 B | 8× A100-80GB |
| **LoRA** (FP16 frozen + FP32 adapters) | **~16 GB** | ~50 M | T4 16 GB / A100-16 GB |
| **QLoRA** (4-bit base + FP16 adapters) | **~7 GB** | ~50 M | Consumer GPU (8+ GB) |

**QLoRA savings vs Full FP32**: ~94% VRAM reduction.

**Key formulas**:
- Full FT: N×4 (weights) + N×4 (grads) + 2×N×4 (Adam) + activations ≈ 112 GB
- LoRA: N×2 (frozen FP16) + L×4 (LoRA) + 2×L×4 (Adam) + small activations ≈ 16 GB
- QLoRA: N×0.5 (4-bit) + L×2 (LoRA FP16) + 2×L×4 (Adam) + tiny activations ≈ 7 GB

## Quick Start

### Local (dataset generation only — no GPU needed)

```powershell
cd task-1-lora-finetuning
pip install -r requirements.txt
python src/generate_dataset.py
```

### Google Colab (training)

1. Upload this repository to Google Drive.
2. Open `notebooks/lora_finetuning_colab.ipynb` in Colab.
3. Set runtime to **GPU** (T4 or better): Runtime → Change runtime type.
4. Update `REPO_PATH` in Cell 5 to match your Drive path.
5. Run all cells in order (Ctrl+F9).
6. Results are saved to `results/` in your Drive.

### Evaluation (after training)

```bash
python src/evaluate.py \
    --test dataset/test.json \
    --predictions results/predictions_finetuned.json \
    --output results/metrics.json
```

## Evaluation Metrics

The `evaluate.py` script computes:

| Metric | Description |
|---|---|
| `json_validity_rate` | Fraction of predictions parseable as valid JSON |
| `action_accuracy` | Exact match rate for the `action` field |
| `field_exact_match_per_field` | Per-field accuracy across all gold fields |
| `overall_exact_match` | Fraction where every gold field matches exactly |
